Start with the user's task and current workspace. The verification service is available directly in ordinary conversations. If the desired tool is deferred, discover it using the available tool search, for example `select:mcp__verification__fsdb_wave`. With `LocalToolSearch`, load the schema and then use `DeferredToolCall` with the exact `name` and an `input` object. Call directly when the method is already listed as a normal tool. The names below refer to tools on the `verification` MCP server. `verification_tool_catalog` lists tools and searchable Chinese/English aliases. Give it a `toolId` of `rtl`, `fsdb` or `coverage` to obtain exact argument schemas, the SDK, the CLI, and native implementation paths.

- **RTL:** Use `design_query` with `operation: instances` to find modules by definition or instance, or `operation: signal` for both drivers and loads. Use the selected build's compiled KDB for `kdb` (e.g. `build/simv.daidir/simv.kdb`). Its containing `simv.daidir` or `kdb.elab++` also works. If the user did not give a path, look for a compiled KDB in their project. When several builds match, ask which to inspect. When none is present, request the compiled KDB with its companion elaboration directory. Keep compilation separate from the query. Poll `design_query_status` with the original jobId. Report source locations and distinguish interface/modport binding direction from actual reads and writes. Keep warnings, partial results and truncation visible.
- **FSDB:** Use `fsdb_files` and `fsdb_signals` to resolve the recorded file and exact signal names. Use `fsdb_wave` with decimal tick strings for a range or with the trigger configuration for pre/post-trigger history. Poll `fsdb_get`. Return the job ID and viewer path, preserve four-state values, and report missing signals and truncated intervals.
- **Coverage:** Use `coverage_extract` with the VCS .vdb path or verification run ID, then poll `coverage_get`. Read the per-test or merged view requested using `coverage_rows`. Follow `nextAfter` until null for a complete aggregation. Preserve excluded objects, unknown counts and uncovered bins as separate states. Include the extraction ID, chosen view and evidence path.

For any query, reuse an existing compatible job ID when supplied. Read the terminal native status and actual results before drawing conclusions. Resolve ambiguous paths or designs against the current project.

When the user asks for reusable or custom analysis, first inspect the catalog for the relevant tool and call `verification_tool_scaffold` with its ID. It returns a project-local Python file under `verification_extensions/` and reports whether it already existed. Read existing files and keep the user's edits when extending them. Adapt or compose the SDK methods with the normal workspace editor and execution tools. Run the resulting script on the requested project inputs, inspect its output, and give the script path, command, native job IDs and verification results. Use `VerificationClient.run` for submissions, `call` for single reads and `coverage_rows` for pagination. The three tools can share one client and workspace. For new native capabilities, use the catalog's implementation paths to locate the code and consult the NPI knowledge base. If its entries lack a needed signature, example or constraint, use `knowledge_read_original` for the cited manual pages. Prefer project-local extensions when the existing API exposes the needed data.
